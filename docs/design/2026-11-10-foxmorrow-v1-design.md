# foxmorrow v1: дизайн

Document status: approved
Дата: 10 ноября 2026 года. Проверено на Devin CLI и Desktop `3000.12.28 (91c3aec41579)`.

## 1. Назначение

foxmorrow координирует разработку набором агентов в Devin. У каждой роли своя модель. Root передаёт агентам контекст через записанные в журнал брифы и принимает результат только по проверяемым доказательствам: кто выполнил работу, на какой модели и какие команды действительно запускались.

foxmorrow написан заново по образцу Agent Flow (`svishniakov/agent-flow`, Codex). Код и журналы Agent Flow не переносятся, совместимости с ними нет.

foxmorrow запускается только явно: маркером `$fox` или `$foxmorrow` в сообщении пользователя либо командой `/foxmorrow:fox`. Hook `UserPromptSubmit` находит маркер и добавляет в контекст указание запустить skill `fox`. Если hook не сработал, то же правило есть в описании skill. Начатая задача продолжается без повторного маркера до `finalize` или отмены.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Переносимость | Ядро не зависит от среды выполнения. В v1 реализуется только адаптер для локального Devin |
| Среды | v1: Devin CLI и Desktop. Devin Cloud: второй этап, отдельный адаптер на том же ядре |
| Доказательства | Квитанции журнала, hooks плагина и сверка с локальной `sessions.db` |
| Координация | Координирует root, то есть сессия, в которой пользователь написал `$fox`, по правилам skill `fox` и журнала. Отдельного субагента в роли оркестратора нет |
| Роли | Все роли Agent Flow, кроме дизайнерских и устаревшей роли `orchestrator` |
| Doc Flow | Входит в v1: цепочка BRD → ADR → PRD → Implementation Plan (или новый ADR, затем план) → реализация плана за один run |
| Язык брифа | Задаётся в плагине (`brief_language` в `profiles/devin.json`). В v1 шаблоны `en` и `ru`, тексты ролей только на английском |
| Язык ядра | Rust, один бинарник `foxmorrow` |
| Независимость проверки | Reviewer и QA работают на другом семействе моделей, чем автор. Правило включено по умолчанию и отключается в профиле; отключение записывается в final |
| Схема `sessions.db` | Reader проверяет только нужные ему поля, карта схемы хранится как данные, извлечения сверяются с положительными якорями. Проверки в CI на новых версиях Devin нет |
| Доставка бинарника | Загрузчик в плагине скачивает бинарник из GitHub Releases и сверяет закреплённый SHA-256 |
| Платформы | macOS arm64 и x64, Linux x64 и arm64, Windows x64 |
| Репозиторий | Новый: `svishniakov/foxmorrow` на GitHub |
| Модели по уровням | Выбраны на этапе 0 по `devin models` и записаны в `profiles/devin.json` (планы 000 и 003) |

## 4. Подтверждённые факты о Devin

Источники: локальная документация Devin (`share/devin/docs`), docs.devin.ai и проба 8 ноября 2026 года. В пробе один субагент `subagent_explore` был запущен из сессии Desktop, затем `sessions.db` прочитана в режиме только для чтения.

1. Собственная роль описывается файлом `agents/<name>.md` с полями `name`, `description`, `model`, `allowed-tools`, `max-nesting`. `allowed-tools` действительно ограничивает доступные инструменты. Функция помечена как experimental.
2. Плагин (`.devin-plugin/plugin.json`) может содержать `skills/`, `agents/`, `AGENTS.md`, `rules/`, `hooks.json` и серверы MCP. Роли плагина доступны как `<plugin>:<name>` только в CLI и Desktop.
3. `run_subagent` принимает профиль, но не модель. Субагент не видит историю родителя. По умолчанию вложенные субагенты запрещены.
4. Hooks получают `session_id` и `prompt_id`. `PostToolUse` получает `tool_name`, `tool_input`, `tool_response`. Hooks плагина работают по принципу best effort: при сбое сессия продолжается без них.
5. Цепочка субагента хранится в `message_nodes` родительской сессии. Таблица `subagent_heads(session_id, agent_id, chain_node_id)` указывает на последнее сообщение цепочки. Остальная цепочка восстанавливается по `parent_node_id`.
6. У каждого ответа субагента есть `chat_message.metadata.generation_model`; в пробе это `swe-2-medium`. Задание субагента сохраняется дословно в сообщении `user` цепочки.
7. Вызов `run_subagent` у root сохраняется в `tool_call_state` с `rawInput.profile`, `rawInput.title`, `rawInput.task`. Результат вызова содержит `agent_id`.
8. Вызовы инструментов субагента имеют собственные ID и статус в `tool_call_state`. Для `exec` записывается `_meta.terminal_exit.exit_code`.
9. Схема `sessions.db` не документирована.

## 5. Архитектура

### 5.1. Состав репозитория

Корень репозитория и есть плагин Devin.

```
.devin-plugin/plugin.json      name: foxmorrow, version, requiredPlugins
bin/foxmorrow                  загрузчик для macOS и Linux (POSIX sh)
bin/foxmorrow.cmd              загрузчик для Windows
checksums.json                 SHA-256 бинарников текущей версии
hooks.json                     UserPromptSubmit, PostToolUse, PostCompaction → foxmorrow hook
skills/fox/SKILL.md            точка входа root
skills/fox/references/         flows, orchestrator, doc-flow (brd, adr, prd, plan), contract
templates/brief.en.md          шаблон брифа на английском
templates/brief.ru.md          шаблон брифа на русском
agents/<role>.md               сгенерированные роли с моделями по умолчанию
roles/roles.json               каталог ролей: уровень, skills, инструменты
roles/<role>.md                тексты ролей без привязки к среде
profiles/devin.json            уровень → модель Devin, правило о семействах
schema-maps/*.json             карты схемы sessions.db
crates/foxmorrow-core/         журнал, контракт, правила приёмки
crates/foxmorrow-devin/        hooks, reader sessions.db, генератор ролей
crates/foxmorrow/              CLI
tests/fixtures/                обезличенные срезы sessions.db
docs/                          README, установка, модель угроз
```

В репозитории нет `AGENTS.md` плагина: правила foxmorrow действуют только после явного запуска через skill.

### 5.2. Границы ответственности

* `foxmorrow-core` хранит задачи, назначения, отчёты, квитанции, наблюдения, снимки и final. Он проверяет правила приёмки. Наблюдения он получает через общий интерфейс, их источник ему неизвестен.
* `foxmorrow-devin` превращает события hooks и записи `sessions.db` в наблюдения, применяет карту схемы и генерирует `agents/*.md`.
* `skills/fox` содержит инструкции для root: когда вызывать какую команду и как передавать брифы.

Адаптер для Devin Cloud на втором этапе станет отдельным крейтом. Наблюдения он будет брать из API событий сессии, а вместо общего checkout передавать ветку. Ядро при этом не меняется: оно с самого начала не предполагает общий checkout.

### 5.3. Данные в проекте пользователя

```
.foxmorrow/
  session                      session_id и prompt_id root (записывает hook)
  profile.json                 необязательные переопределения моделей и правила о семействах
  runs/<run_id>/journal.sqlite журнал задачи
  memory/todo.md
  memory/lessons.md
  memory/notes.md
.devin/agents/fox-<role>.md    проектные роли, только для ролей с переопределённой моделью (создаёт foxmorrow sync)
```

## 6. Роли и модели

### 6.1. Состав

| Группа | Роли |
|---|---|
| Требования и архитектура | `product-manager`, `architect`, `supervising-architect`, `researcher`, `documenter`, `ai-slops-hunter`, `marketing-growth-strategist`, `rag-retrieval-engineer` |
| Исполнители | `astro-worker`, `backend-worker`, `bun-worker`, `devops-worker`, `elixir-phoenix-worker`, `frontend-worker`, `golang-worker`, `ios-worker`, `python-worker`, `typescript-worker` |
| Проверка | `reviewer`, `qa-verifier`, `senior-qa-verifier` |

Не переносятся `design-asset-generator`, `design-documenter`, `design-orchestrator`, `pencil-designer`, `ui-reference-researcher`, `ui-ux-design-director`, `ui-ux-designer`, `visual-qa` и `orchestrator`.

Координирует root. Отдельный субагент в роли оркестратора не нужен, потому что в Devin:
* субагент по умолчанию не может запускать субагентов;
* субагенту недоступен `ask_user_question`;
* фоновый субагент не может запросить разрешения.

Root работает на модели, выбранной пользователем в Devin. `init` записывает её фактическое значение из `sessions.db` в run, а `finalize` повторяет его в final.

Роли и модели задаются на уровне плагина и проекта. Назначения создаются только внутри задачи (run): одна роль может получить в run несколько назначений, каждому из них соответствует отдельный запуск субагента.

### 6.2. Уровни и модели

В `roles/roles.json` роли назначается уровень. Конкретная модель для каждого уровня задаётся в `profiles/devin.json`.

| Уровень | Роли |
|---|---|
| `worker` | все `*-worker`, `ai-slops-hunter`, `researcher` |
| `analyst` | `architect`, `product-manager`, `documenter`, `rag-retrieval-engineer`, `marketing-growth-strategist` |
| `verifier` | `reviewer`, `qa-verifier` |
| `escalation` | `supervising-architect`, `senior-qa-verifier` |

ID моделей выбираются на этапе 0 по списку `devin models`. Плагин поставляет роли `foxmorrow:<role>` с моделями по умолчанию; каталог `agents/` плагина общий для всех проектов и перезаписывается при обновлении плагина, поэтому проектные настройки в него не пишутся.

Переопределение для проекта:
* пользователь задаёт модель для уровня или роли в `.foxmorrow/profile.json`;
* `foxmorrow sync` создаёт `.devin/agents/fox-<role>.md` только для переопределённых ролей;
* `assign` выбирает профиль для брифа: проектный `fox-<role>`, если он есть, иначе `foxmorrow:<role>`, и записывает в назначение профиль и ожидаемую модель;
* `verify` сверяет `generation_model` с моделью именно этого профиля;
* `foxmorrow sync --check` сообщает о расхождении `agents/` плагина с `roles/` и `profiles/devin.json`, а проектных ролей с `.foxmorrow/profile.json`.

Правило о семействах: если оно включено, все ответы в цепочках `reviewer` и `qa-verifier` должны прийти от модели другого семейства, чем модель автора назначения из `depends_on`. Таблица соответствия ID модели и семейства хранится в `profiles/devin.json`.

### 6.3. Инструменты

| Роль | Ограничение `allowed-tools` |
|---|---|
| `reviewer`, `researcher`, `qa-verifier`, `senior-qa-verifier` | чтение, поиск, `exec`; без `edit` и `write` |
| исполнители и роли документов | полный набор |

`exec` нужен всем ролям, потому что отчёт сдаётся командой `foxmorrow report`. Через `exec` технически можно изменить файлы, и C5 такие изменения не обнаруживает: журнал не сканирует рабочий каталог. Это ограничение указано в модели угроз.

Фоновые субагенты не могут запросить новые разрешения. Поэтому root запускает авторов на переднем плане либо заранее просит пользователя выдать нужные разрешения.

### 6.4. Зависимости от skills

* `arch-simplicity-guard` подключается через `requiredPlugins` манифеста.
* Профильные skills ролей перечислены в `roles/roles.json`. Их наличие проверяется до начала работы:
  * `foxmorrow init` проверяет skills всех ролей и выдаёт root сводку недостающих; задача не останавливается, root может попросить пользователя установить skill;
  * `foxmorrow assign --role R` повторяет проверку для роли R. Если skill отсутствует, назначение не создаётся, пока root явно не подтвердит работу без него флагом `--allow-missing-skills`. Тогда `missing_skills` записывается в назначение и указывается в брифе, а субагент в отчёте описывает решения, принятые без правил skill;
  * `foxmorrow doctor` выполняет ту же проверку вне задачи.
* Способ получить список доступных Devin skills проверяется на этапе 0 (пункт 8). Если машиночитаемого способа нет, проверка идёт по известным каталогам skills и помечается как приблизительная.

## 7. Поток задачи

```
$fox … → root (skill fox)
  init → [product-manager, architect по необходимости]
       → assign авторов → verify
       → assign reviewer → verify
       → assign qa-verifier → verify
       → finalize
```

1. `foxmorrow init --criteria <файл#раздел> --paths …` создаёт run. В него записываются:
   * источник критериев: раздел задачи с подразделом «Критерии приёмки»;
   * для каждого репозитория HEAD, remote refs и незакоммиченные изменения;
   * разрешённые пути;
   * `session_id` root из `.foxmorrow/session`, а если hook не сработал, из `sessions.db` по cwd и последней активности;
   * фактическая модель root;
   * сводка недостающих skills.
2. `foxmorrow assign --role R [--depends-on ID…] [--previous ID] [--allow-missing-skills] --paths …` создаёт назначение и печатает бриф. Root передаёт бриф дословно в `run_subagent` с профилем, который выбрал `assign` (§6.2). Бриф отрисовывается по шаблону `templates/brief.<brief_language>.md`. Если для языка нет шаблона, назначение не создаётся. Бриф содержит:
   * `assignment_id`, хеш брифа и язык;
   * блок роли: имя, профиль, хеш текста роли (`role-sha256`), ожидаемая модель, skills для применения и `missing_skills`;
   * цель и критерии;
   * разрешённые пути;
   * итоги и ссылки на отчёты из `depends_on`;
   * формат отчёта и команды `check` и `report`.

   Переводится только текст для агента. Идентификаторы, команды, ключи и значения отчёта в JSON, пути и ID критериев одинаковы во всех языках; цель и критерии переносятся из исходного документа без перевода. Текст роли в бриф не копируется: Devin передаёт его системным промптом субагента.
3. `foxmorrow check -a A -- <команда>` выполняет команду один раз. Квитанция содержит cwd, argv, exit code, время, хеш и ограниченный фрагмент вывода.
4. `foxmorrow report -a A` читает отчёт из stdin. Поля отчёта:
   * `summary`: непустая строка;
   * `status`: `completed` или `interrupted`;
   * `outcome`: `passed`, `failed` или `unverified`;
   * `criteria`: для каждого критерия статус, `reason` и ссылки;
   * `evidence`: ID квитанций и вызовов инструментов;
   * `resolves`: для повторной проверки ссылки на прежние отрицательные отчёты.
5. `foxmorrow verify -a A` вызывает root. Команда связывает назначение с `agent_id` и проверяет утверждения C1–C6 из §8.2. Результат: отчёт принят или отклонён с перечнем причин. Принятый отчёт больше не меняется.
6. Исправление оформляется новым назначением с `--previous`. Root направляет замечания:
   * дефект реализации автору;
   * архитектурную проблему `architect`;
   * недостаток доказательств проверяющему;
   * спорные решения `supervising-architect` или `senior-qa-verifier`;
   * недостающие сведения или ручные действия человеку.
7. `foxmorrow finalize --report ID` закрывает run по итоговому QA либо по отчёту root об окончательной остановке. Неположительный final требует причины и списка непроверенного.
8. `foxmorrow status` выводит текущее состояние run для root.

Порядок приёмки обеспечивает журнал:
* reviewer зависит от завершённых авторских отчётов;
* QA зависит от review с `status: completed` и `outcome: passed`;
* final выбирает отчёт, у которого подтверждены все обязательные утверждения.

### 7.1. Doc Flow

Документы готовятся по той же механике, только продуктом считается документ. Каждый документ создаётся или пересматривается отдельным run.

Цепочка документов:

```
BRD → ADR → PRD (по одному на фичу) ─┬→ Implementation Plan → реализация
                                     └→ ADR (если меняется архитектура) → Implementation Plan → реализация
```

| Тип | Автор | Участие других ролей |
|---|---|---|
| `brd` | `product-manager` | `marketing-growth-strategist` даёт данные о рынке отдельным назначением, когда они нужны |
| `adr` | `architect` | `supervising-architect` по спорным решениям |
| `prd` | `product-manager` | |
| `plan` | `architect` | `supervising-architect` по спорным решениям |

Порядок для всех типов один. Автор пишет документ и для русского текста применяет `humanizer-ru`. Отдельный `ai-slops-hunter` редактирует результат, после чего документ проверяют независимые `reviewer` и QA. Правила содержания PRD и ADR переносятся из Agent Flow; порядок и содержание BRD описываются заново.

Правила цепочки:
* В заголовке документа есть `Document status: draft|approved` и `Based on:` со ссылками на вышестоящие документы: первый ADR ссылается на BRD, PRD на BRD и ADR, новый ADR фичи на свой PRD, план на PRD и, если есть, на новый ADR.
* Документ с открытыми вопросами не может получить статус `approved`. Содержательный вывод проверки документа: `PASS` или `FAIL`; он не утверждает документ.
* `foxmorrow init --doc <тип> --based-on <путь…>` не начинает работу над документом, если хотя бы один документ из `Based on` не утверждён или содержит открытые вопросы.
* После утверждения PRD root вместе с `architect` решает, нужен ли новый ADR, и записывает решение и причину в run PRD. Если архитектура меняется, а нового ADR нет, план не допускается к утверждению.

### 7.2. Реализация плана

```text
$fox Реализуй план docs/implementation/impl-004-health.md
```

1. Root вызывает `foxmorrow init --plan <путь>`. Команда проверяет, что план утверждён и у всей цепочки `Based on` тоже статус `approved`; иначе run не создаётся.
2. Критерии берутся из раздела плана «Критерии приёмки». Внешняя настройка, удалённый CI и живые проверки выделяются в отдельные задачи со своими критериями, как в Agent Flow.
3. Каждый бриф ссылается на нужные разделы плана, PRD и ADR, а не копирует их.
4. Один план реализуется за один run и закрывается одним `finalize`.
5. Если в ходе реализации выясняется, что план или ADR неверен, root останавливает зависимую часть и создаёт задачу на пересмотр документа отдельным run. Документ не правится по ходу реализации.

### 7.3. Сбои

| Ситуация | Поведение |
|---|---|
| Root потерял контекст после сжатия | Hook `PostCompaction` возвращает в контекст вывод `foxmorrow status` |
| Hook не сработал | `verify` использует `sessions.db`. Если нет обоих источников, утверждение получает `unverified` |
| Субагент прерван | Отчёт со `status: interrupted`. Root проверяет фактический результат внешней команды, прежде чем повторять её |
| Квитанция `check` не записана после прерывания | Команду можно повторить только после проверки её фактического результата |

## 8. Доказательства

### 8.1. Источники

1. Квитанции журнала. Самый надёжный источник, не зависит от Devin.
2. `sessions.db` в `~/.local/share/devin/cli/` (путь меняется через `DEVIN_SESSIONS_DIR`). Открывается только в режиме `mode=ro`. Это единственный источник для проверки модели.
3. Hooks плагина. `foxmorrow hook <event>` дописывает наблюдения:
   * `UserPromptSubmit`: `session_id`, `prompt_id`, маркер;
   * `PostToolUse` для `run_subagent`, `exec`, `edit` и `write`;
   * `PostCompaction`.

   Hooks отказывают открыто и ничего не подтверждают в одиночку.

### 8.2. Утверждения

| ID | Утверждение | Подтверждение |
|---|---|---|
| C1 | Доставка поручения и роли | Вызов `run_subagent` с профилем, записанным в назначении, и task, содержащим `assignment_id` и хеш брифа. Из результата берётся `agent_id`. В системных сообщениях цепочки есть текст роли с хешем `role-sha256` из назначения |
| C2 | Авторство отчёта | Вызов `foxmorrow report -a A` есть в цепочке этого `agent_id` |
| C3 | Модель | Все ответы цепочки имеют `generation_model` из профиля роли; при включённом правиле семейство отличается от автора |
| C4 | Действия | Ссылки отчёта указывают на вызовы этой цепочки, exit code совпадает с заявленным, квитанции `check` принадлежат назначению и вызваны из его цепочки |
| C5 | Независимость | `agent_id` проверяющего не совпадает с автором; в цепочках `reviewer` и `qa-verifier` нет `edit` и `write` |
| C6 | Порядок | Условия `depends_on` выполнены |

Final со статусом `passed` возможен, только если у выбранного отчёта и у всех отчётов в его `depends_on` подтверждены C1–C6. Текст отчёта не считается доказательством.

### 8.3. Карта схемы и якоря

* `schema-maps/*.json` описывают таблицы, колонки, запросы SQL и пути JSON, которыми пользуется reader. Бинарник только интерпретирует карту.
* Reader проверяет наличие нужных ему таблиц, колонок и путей. Дополнительные таблицы и колонки он игнорирует.
* Каждое извлечение должно совпасть с положительными якорями:
  * в task цепочки есть `assignment_id` и хеш брифа;
  * в системных сообщениях цепочки есть текст роли с `role-sha256`;
  * цепочка непрерывна от задания до последнего ответа;
  * ID вызовов из отчёта найдены в этой цепочке;
  * у каждого ответа есть `generation_model`.
* Если якоря не совпали или нужные поля отсутствуют, источник считается `unavailable`, а зависящие от него утверждения получают `unverified`.
* Изменение схемы Devin, которое ломает карту, исправляется новой картой в обновлении плагина, без пересборки бинарника.
* `foxmorrow doctor` сообщает, какая карта подошла и каких полей не хватает.

### 8.4. Неизменяемость

`verify` сохраняет снимок нужных нативных записей: идентификаторы, хеши и фрагменты. `finalize` перепроверяет сохранённые снимки, а не живую базу. Последующая очистка истории Devin не меняет принятых результатов.

### 8.5. Модель угроз

foxmorrow защищает от того, что агент заявляет несделанную работу как выполненную, путает роль или модель, подменяет отчёт или назначение. Изменения файлов проверяющей ролью через `exec` не обнаруживаются. Защиты от пользователя, который вручную правит `sessions.db` или журнал, нет; в документации это сказано явно.

## 9. Дистрибуция и выпуск

### 9.1. Установка и запуск

```sh
devin plugins install svishniakov/foxmorrow
```

`bin/foxmorrow` и `bin/foxmorrow.cmd` при первом вызове скачивают бинарник своей версии и платформы из GitHub Releases, сверяют SHA-256 из `checksums.json` и сохраняют его в пользовательский кеш (`~/.cache/foxmorrow/<version>/` или аналог на Windows). Последующие вызовы запускают бинарник из кеша. Бинарник другой версии загрузчик не запускает. Если скачать не удалось, загрузчик завершается с понятной ошибкой: hooks отказывают открыто, `verify` возвращает `unverified`, `doctor` показывает причину.

### 9.2. Выпуск по тегу `vX.Y.Z`

1. CI собирает `foxmorrow` для `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-pc-windows-msvc`.
2. Считает SHA-256 и создаёт GitHub Release.
3. Обновляет `checksums.json` и `version` в `.devin-plugin/plugin.json`. Версии плагина, загрузчика и бинарника всегда совпадают.

### 9.3. Проверки

* На каждый push: `cargo fmt --check`, `cargo clippy -- -D warnings` и `cargo test` на macOS, Linux и Windows.
* Ядро:
  * переходы состояний;
  * неизменяемость отчётов;
  * порядок приёмки;
  * правило о семействах;
  * Doc Flow: документ с открытыми вопросами не утверждается;
  * цепочка документов: `init --doc` и `init --plan` отказывают при неутверждённом документе в `Based on`;
  * `assign` без `--allow-missing-skills` не создаёт назначение для роли с недостающим skill;
  * бриф на `en` и `ru` даёт одинаковые идентификаторы, команды и ключи отчёта; неизвестный язык отклоняется;
  * выбор профиля: проектный `fox-<role>` при переопределении, иначе `foxmorrow:<role>`.
* Reader:
  * fixtures `sessions.db`, включая цепочку субагента из пробы;
  * карта с отсутствующими полями и несовпадающими якорями даёт `unverified`, а не `passed`.
* Генератор: `foxmorrow sync --check` для `agents/*.md`.
* Перед выпуском локально: `devin doctor` на каталоге плагина.
